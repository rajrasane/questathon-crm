# Account Brief — implementation thinking

**The problem.** An account handover contains claims, documents, contacts, opportunities and later changes. Reading all of them does not automatically reveal the next decision. Account Brief organizes that evidence into a commercial position, stakeholder assessments and three proposed actions for each account.

**What the interface prioritizes.** The overview shows existing annual contract value separately from opportunity and newly booked value, followed by ranked actions and dated changes. Deals, people and evidence have dedicated views. Reasons, outcomes, risks, questions and source details expand on demand. This makes the first screen usable without removing the underlying evidence.

**Evidence before certainty.** Claims, told/reported statements, verified records and interpretations keep different labels. Every non-unknown statement must reference a source that exists. Missing values stay unknown; currencies are not guessed; offers do not become revenue. A past signature identifies a historical signatory, not current buying authority. Conflicting savings statements remain separate. A measured usage stoppage does not establish its cause or location.

**How recommendations work.** A deterministic server-side analyzer combines discovery, contract/profile records, merged requests, dated signals and usage calculations. It prioritizes urgent unresolved requests, succession gaps, sustained usage stoppages, commercial requests and supported evidence conflicts. Owners and follow-up dates are visibly proposed. Closing a request removes it from the candidate actions. These explicit rules are repeatable and testable, but they do not replace customer discovery or exhaustively interpret every document.

**Fetch once, then update.** A Node server validates the MCP envelope and JSON text payload, fetches each missing baseline resource once and caches it. Subsequent checks merge signals by account/event ID, requests by stable row key and usage by device/week. Repeated content is a no-op; changed content regenerates the brief. The upstream token stays server-side. Every network attempt reserves a 61-second request budget before I/O, including failures. Exactly one selected environment owns ingestion; no automatic notes are written.

**Hosting and verification.** The local implementation uses private files and atomic replacement. The Vercel adapter uses one persistent Redis state document, an atomic shared cooldown, a fenced ingestion lease and a protected scheduled endpoint. This avoids relying on serverless temporary files or persistent timers. Tests cover provenance, nulls, transport decoding, caching, concurrency, repeat updates and failure recovery. Browser checks cover both accounts, source inspection, keyboard controls and phone layouts. Production storage, scheduling, credential configuration and private-window acceptance must be verified on the actual deployment before calling delivery complete.

**Tradeoff.** The app deliberately exposes uncertainty instead of manufacturing a complete CRM. Its value is a traceable next conversation: what needs attention, why it matters, who should own it, what outcome is sought and which evidence could change the recommendation.
