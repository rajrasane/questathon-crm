# Account Brief — implementation thinking

**The problem.** An account handover contains claims, documents, contacts, opportunities and later changes. Reading all of them does not automatically reveal the next decision. Account Brief organizes that evidence into a commercial position, stakeholder assessments and three proposed actions for each account.

**What the interface prioritizes.** The portfolio compares accounts, filters recorded opportunity stages and surfaces the next conversations. Account views separate existing contract, opportunity and newly booked value. Flight charts link to source rows and show device coverage; missing weeks are not zero. Deals, people and evidence have dedicated views. Reasons, risks and source details expand on demand. Consistent navigation and status labels help a new owner orient quickly.

**Evidence before certainty.** Claims, told/reported statements, verified records and interpretations keep different labels. Every non-unknown statement must reference a source that exists. Missing values stay unknown; currencies are not guessed; offers do not become revenue. A past signature identifies a historical signatory, not current buying authority. Conflicting savings statements remain separate. A measured usage stoppage does not establish its cause or location.

**How recommendations work.** A deterministic server-side analyzer combines discovery, contract/profile records, merged requests, dated signals and usage calculations. It prioritizes urgent unresolved requests, succession gaps, sustained usage stoppages, commercial requests and supported evidence conflicts. Owners and follow-up dates are visibly proposed. Closing a request removes it from the candidate actions. These explicit rules are repeatable and testable, but they do not replace customer discovery or exhaustively interpret every document.

**Fetch once, then update.** A Node server validates the MCP envelope and JSON text payload, fetches each missing baseline resource once and caches it. Released accounts are discovered through the upstream access directory and use the same analysis path. Later checks merge signals by account/event ID, requests by stable row key and usage by device/week. Repeated content is a no-op; changed content regenerates the brief. The upstream token stays server-side. Every network attempt reserves a 61-second request budget before I/O, including failures. Exactly one selected environment owns ingestion; no automatic notes are written.

**Hosting and verification.** The local implementation uses private files and atomic replacement. Production uses Vercel, private Redis persistence, an atomic cooldown and fenced lease, with a protected QStash trigger every two minutes. The browser reads the cache; status separates completed checks, pending work and evidence gaps. Tests cover provenance, nulls, transport, concurrency, idempotence and chart merging. Browser checks cover evidence drawers, stage filters, keyboard controls and phone layouts. Production checks verified persistent storage, MCP reads, a scheduled signal check, unchanged-response idempotence and a fresh browser session. Changed-signal behavior is tested with synthetic records; a new live event is not claimed.

**Tradeoff.** The app deliberately exposes uncertainty instead of manufacturing a complete CRM. Its value is a traceable next conversation: what needs attention, why it matters, who should own it, what outcome is sought and which evidence could change the recommendation.
